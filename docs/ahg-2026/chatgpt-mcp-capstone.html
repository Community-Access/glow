Presenter capstone: PSY 101 in ChatGPT with GLOW tools

1. Purpose and boundaries

Show this at the front of the room. Participants watch; they do not need a paid account, administrator permissions or their own server connection. Use the fictional PSY 101 course already developed for this workshop. Do not use a real campus site, student information or accommodation records.

The lesson: reviewed agent instructions define the job; a Model Context Protocol (MCP) connection supplies tools; a person reviews the result. Connecting a server does not publish the agent, grant campus-system access or make a course accessible.

No plugin package upload or public-directory submission is needed. ChatGPT may call the connection a plugin and its button "Create as a plugin". That registers our existing hosted server, not a package of our code.

Three sharing routes remain useful:

  1. A versioned instruction document in an approved shared location.
  2. Skills in a shared VS Code project for coworkers already using Copilot.
  3. Reviewed instructions plus an approved assistant's shared tool connection.

An application-specific plugin can package skills and tools where supported. It is not a universal upload for every assistant. Building a new server or application is outside this demonstration.

3. Account and policy checks

  1. Use ChatGPT on the web with the presenter account.
  2. Confirm the selected workspace is approved for the demo. Do not project account settings, email, billing, private chats or administrator pages.
  3. Confirm that custom MCP connections are available to that account. OpenAI's documentation checked on 13 November 2026 lists full support for Business and Enterprise/Edu. Do not promise access on a participant's Free, Plus or Pro account; check the actual account and current guidance.
  4. On Business, an administrator or owner creates and publishes connections. On Enterprise/Edu, an administrator can also authorize selected developers to create connections. Only administrators or owners publish workspace connections. Request approval rather than bypassing a restriction.
  5. Obtain approval to send the fictional course HTML to ChatGPT and GLOW. The content goes through both services. Public availability is not a substitute for institutional approval.

4. Connect ChatGPT to the existing server

The current interface may differ from the older Apps interface. Follow the labels actually present; do not repeatedly change security settings to find a missing control.

  1. Before sharing your screen, open ChatGPT's Plugins page.
  2. Select the plus button, then "Add custom MCP server".
  3. Enter the name GLOW Accessibility - AHG Demo.
  4. Enter the description Read-only PSY 101 accessibility checks for the AHG presenter demonstration.
  5. Choose the remote connection and enter https://letitglow.app/a11y/mcp as the HTTPS endpoint. Do not enter the GLOW home page, the course URL or localhost.
  6. For the currently public endpoint, select no authentication if offered. If it now requests authentication, stop and confirm the server's actual requirements with its owner; do not enter unrelated credentials.
  7. Review the risk warning and discovered tools before accepting.
  8. Select "Create as a plugin", then install or enable the resulting connection for the presenter account if prompted.
  9. Confirm these tool names appear: check_heading_structure, check_link_text and check_contrast.
  10. Review all other exposed tools as well. Limit enabled tools to those three if the workspace offers action controls. Otherwise do not describe the entire connection as technically read-only: the server also exposes document-processing and alt-text-writing capabilities.
  11. Start a new chat. Type @ and select the GLOW connection. Confirm it is selected on each later message that requests tools; selection may apply to one message rather than the whole conversation.
  12. Run the smoke prompt below. Inspect its actual tool call and result.
Use the selected GLOW Accessibility connection to call check_contrast with
foreground "#b5b5b5" and background "#ffffff". Report the returned ratio,
the AA normal-text threshold, and the actual tool name. Do not estimate.
If the connection cannot run, say "Not checked" and explain the error.

Expected: check_contrast returns approximately 2.05:1, below 4.5:1. The tool result must be visible. A model-generated number alone is not proof.

If you see the legacy Apps interface instead:

  1. Open workspace Settings, Apps, Create, or user Settings, Apps, Create if your role is authorized.
  2. Enter the same name and endpoint and the verified authentication choice.
  3. Select Scan Tools, review the results and select Create.
  4. Select the resulting draft connection in a fresh chat and run the same smoke prompt. If the interface requires an older developer-mode control, consult the linked current OpenAI instructions and workspace admin. The current Plugins workflow does not require that toggle.

Expected result: one genuine successful tool call, with date and account workspace recorded locally. Connection creation alone is not a pass.

6. Run the three real checks

  1. Confirm the GLOW connection is selected for this message.
  2. Paste and send this exact request.
Use the GLOW connection now:
1. Call check_heading_structure with the complete supplied HTML.
2. Call check_link_text with the same complete HTML.
3. Call check_contrast with foreground "#b5b5b5" and background "#ffffff".
Use each tool's exact input schema. Do not send a URL in place of HTML.
Show a short summary of each returned result and identify its tool.
If any call fails or is unavailable, mark that check "Not checked".
Do not replace it with a guessed result or a different service.
  1. Review any approval request. Approve only the intended checks and fictional input. Decline an unexpected file-write or unrelated action.
  2. Expand the tool activity. Read the actual tool name, arguments and returned result aloud; do not expose private account information.
  3. Compare against this baseline, measured directly against the public MCP endpoint on 13 November 2026:
    • check_heading_structure: one reported jump, from h1 to h4 at "What to do this week". The source has two h4 headings.
    • check_link_text: two ambiguous links, "Click here" to the lecture PowerPoint and "Read more" to the syllabus.
    • check_contrast: 2.05:1 for #b5b5b5 on #ffffff. Normal text needs at least 4.5:1; large text needs 3:1. This pair fails both.
  4. If results differ, inspect the input and server version before proceeding. Do not change the sample or invent matching output to hide the difference.
  5. Save the actual tool outputs in your approved rehearsal evidence location, not in the public participant kit.

The tools inspect supplied HTML and colors. They do not fetch or crawl the course, render computed styles, test keyboard behavior, check every image, open the syllabus or verify the entire course. This is a narrow capstone, not a full audit. Do not replace these checks with scan_uploaded_document during the live presentation.

7. Turn evidence into a useful draft

  1. In the same conversation, send this prompt.
Using the actual returned results, draft a short coaching note to the
fictional instructor. Separate:
1. Tool evidence, naming the tool and exact observation or measurement.
2. Source observations that those three tools did not test.
3. Manual checks still required.

Include a suggested heading structure and descriptive replacement link
labels, but do not modify a file. Explain who is affected.
Flag the clickable div labelled "Submit reflection" for keyboard and
screen reader review. Do not claim you operated it.
Do not invent image descriptions, missing scan results or a compliance score.
Link relevant WCAG 2.2 guidance. End with "Before you send this".
This is a draft for a person to review, not a message to send.
  1. Check that the draft retains the measured ratio and real link labels.
  2. Check that it does not call the whole course scanned, repaired or compliant.
  3. Check that the heading warning is reviewed in context, rather than treated as an unconditional conformance verdict.
  4. Check that it proposes human review before sending and does not send anything.

Possible replacement labels are "Week 3 lecture slides" and "Updated PSY 101 syllabus". The draft must preserve the correct destinations. Wording may vary. Use the facilitator answer key to review additional source observations; do not expect these three tools to find all planted barriers.

8. Show what tools did not establish

  1. Return to the fictional announcement tab.
  2. Using only Tab and Shift+Tab, locate the two links and try to reach "Submit reflection". Do not activate it or submit anything.
  3. Describe what actually happens. The supplied source uses a clickable div without normal keyboard-button semantics; verify the browser behavior rather than claiming the MCP tools tested it.
  4. Explain that an image without alternative text and color-only deadline instructions also need review; neither was covered by these three calls.
  5. Say: "The agent drafted advice. A person still checks the evidence, tests the experience and approves the message."

Expected result: the audience can distinguish a tool measurement, a source observation and a real interaction test. Include a screen reader pass during rehearsal, with the actual browser and assistive technology versions recorded.

10. Explain team rollout without changing the workspace live

  1. Name an owner for the agent instructions and an owner for the connection.
  2. Put reviewed instructions in an approved, versioned shared location.
  3. Have the administrator vet the server, data flow and all exposed tools. A public no-auth endpoint is not a private campus service.
  4. Where supported and approved, the administrator publishes the connection to the intended workspace audience and configures available action/access controls. Use the current OpenAI instructions linked in section 2.
  5. Have a second authorized user open a new chat, select the approved connection, load the same reviewed instructions and repeat the three checks on the same fictional HTML.
  6. Record whether the second user can reproduce the baseline without administrator rights. Do not count the presenter's successful chat as proof of team access.
  7. Record instructions version, server tool names/date, permitted data, reviewer, feedback route and review date.
  8. Define the stop rule: suspend use for unexpected data exposure, unverifiable results, missing required review or changed/unapproved capabilities. The administrator can disable the connection and the owner can withdraw the instructions; keep the existing manual process available.

Publishing a connection does not distribute each participant's agent. Sharing a conversation is not managed deployment. Do not promise automatic updates, identical model answers or cross-platform compatibility.

If workspace publication is not approved, mark team deployment Pending. The presenter capstone can still pass if its own live checks succeed and the unverified rollout is clearly described as a next step.

11. Troubleshooting and day-of preflight

If connection creation is absent, confirm the account, workspace, role and current plan support with the administrator. Do not request a paid upgrade from participants or bypass policy.

If tool discovery fails:

  1. Check that the URL ends in /a11y/mcp.
  2. Check the public course page and GLOW health page separately. A healthy web app alone does not prove the MCP service works.
  3. Ask the server operator to check the MCP service and reverse proxy. A browser GET error on the endpoint is not conclusive; MCP uses protocol requests, including POST. Do not redeploy or reconfigure production merely to troubleshoot this guide.
  4. After a confirmed fix, refresh discovered tools if supported, then retest in a fresh conversation.

If ChatGPT answers without a tool call, reselect the connection on that message and repeat section 6 once. If it still cannot call, mark Blocked and use the labelled fallback. Do not repeatedly prompt it into asserting success.

If source or expected counts differ, compare with the unchanged repository HTML. Check for copying rendered text or only a fragment of the source. Record the difference; rerun only after its cause is understood.

Before the room opens:

  1. Confirm the prepared presenter account and connection still work.
  2. Run the contrast smoke test in a fresh chat.
  3. Confirm the source page and complete local HTML open.
  4. Open this guide and the updated local slide deck offline as backups.
  5. Prepare a chat containing sections 5's instructions and source, but not a fabricated tool result. Save a separate successful rehearsal conversation.
  6. Close private tabs, hide notifications, and check projector zoom, captions and keyboard focus.
  7. Confirm the saved-output fallback is readable without a network.
  8. Open the capstone slide and start the timer. Stop at eight minutes.
